# 0003. Logs

- **Status:** Implementable
- **Authors:** @bhatnagar-afk
- **Created:** 2026-11-15
- **Milestone:** M3

## Summary

KubeRoot shows container logs in the detail panel: for one pod, or merged across every pod of a
workload (Deployment, StatefulSet, DaemonSet, ReplicaSet, Job) or Service. Logs stream live
(follow), can show the previous (crashed) container, can be searched and filtered in place,
and can be downloaded to a file. Workloads and Services also get a **Pods** tab listing their
pods, which proposal
[0002](0002-resource-browsing.md) deferred to M3 (follow-up 1), because both features need the
same "pods of a workload" lookup.

## Motivation

After "what is running?" (M2), the next question is almost always "why is it failing?", and
the answer is usually in the logs. `kubectl logs` handles one pod at a time, makes you find the
pod name first, and loses its place when a container restarts or the connection drops. A
desktop client can do better: open logs from the object you are already looking at, follow a
whole Deployment, and keep streaming across restarts and reconnects.

### Goals

1. A **Logs** tab in the detail panel for pods, workloads and Services.
2. **Follow** (live streaming) with auto-scroll that pauses when the user scrolls up.
3. Options: container (including init and ephemeral containers, or all containers), tail
   lines, since, **previous** container, a timestamps toggle, line wrap.
4. **Workload logs:** lines from all of a workload's (or Service's) pods in one view, prefixed
   with pod and container, following pods as they are created and deleted. No limit on the
   number of pods. A workload shows only pods it owns, never another workload's.
5. **Search:** highlight matches with next/previous, optionally show only matching lines;
   plain text or regex, case-sensitive or not.
6. **Download** the full log of the current target to a file, or **save the received lines**
   (respecting "Only matching").
7. Streams survive container restarts (while following) and connection drops (resume where
   they stopped, without duplicate lines).
8. A **Pods** tab for workloads and Services, live, using the same table pipeline as M2.
9. A noisy pod (tens of thousands of lines per second) must not freeze the UI or grow memory
   without bound. UI memory stays flat however long a stream runs: received lines are kept on
   disk, and the view loads only what is near the screen.

### Non-goals

- Exec, attach, port-forward (post-v0.1).
- Log aggregation across clusters, or from logging backends (Loki, CloudWatch, ...).
- Parsing structured logs (JSON fields as columns). Lines are shown as text.
- Rendering ANSI colours. Escape codes are stripped in M3 (see [Line handling](#line-handling)).
- Node or control-plane logs (`/logs` on the kubelet).
- Pods of CronJobs (they belong to its Jobs) and of custom workload types (e.g. Argo Rollouts).

## Proposal

### User experience

```
┌──────────────┬─────────────────────────────┬──────────────────────────────────────────────────┐
│ prod-eu ●    │ Deployments  [ns: web ▾] 🔍  │ web   Describe | YAML | Events | Pods | Logs  ⤢  │
│ Workloads    │ NAME   READY  UP-TO-DATE AGE│ [All containers ▾] [Tail 1000 ▾] [Since ▾]       │
│  Pods        │ web    3/3    3          3d ◀│ [All pods ▾] ☑ Follow ☐ Previous ☐ Timestamps ☑ Wrap │
│  Deployments◀│ api    1/1    1          9d │ 🔍 timeout   [Aa] [.*] [Only matching] 2/14  ⤓ ▾ │
│  ...         │                             │ web-7d9f-x2  app  GET /health 200                │
│              │                             │ web-7d9f-k8  app  upstream timeout after 30s     │
│              │                             │ web-7d9f-x2  app  GET /orders 504                │
│              │                             │ ── web-7d9f-k8/app restarted ──                  │
│              │                             │                          [↓ Jump to latest]      │
└──────────────┴─────────────────────────────┴──────────────────────────────────────────────────┘
```

- Pods, the five workload kinds and Services get a **Logs** tab. Workloads and Services also
  get a **Pods** tab, a live table of their pods; clicking a row opens that pod in the panel. A
  Service without a selector (ExternalName, or endpoints managed by hand) shows "This Service
  does not select pods" in both tabs.
- Opening the Logs tab starts streaming the last **1,000 lines** per container with follow on
  and line wrap on. Timestamps are off; the **Timestamps** and **Wrap** toggles apply at once,
  without restarting the stream.
- The container defaults to the pod's `kubectl.kubernetes.io/default-container` annotation,
  then to its first container, like `kubectl logs`. For a workload the same rule is applied to
  its pod template. A Service has no pod template, so each pod uses its own default.
- The **⤢** button maximizes the detail panel over the table, since logs need width. Esc or ⤢
  restores it.
- Scrolling up pauses auto-scroll (the stream keeps running) and shows **Jump to latest**.
  Scrolling further up loads older lines as it goes, back to the first line received. The
  footer shows the position (`line 12,345 of 480,112`) and offers **Jump to first**.
- Changing an option restarts the stream with the new options; the old lines are cleared.
- Container restarts and stream gaps are marked inline (`── web-7d9f-k8/app restarted ──`,
  `── disconnected, resumed ──`).
- Workload and Service logs stream **every** matching pod. A pod picker (default **All pods**)
  narrows the view to chosen pods.
- **Download (⤓)** opens a save dialog and writes the full log (not just what is loaded) with
  the current container, previous and timestamps options. Its menu (▾) also offers **Save
  received lines**, which writes every line the stream has received (only the matching lines
  when "Only matching" is on).
- Per-source problems (no permission for `pods/log`, container still creating, pod gone) show
  in a status strip above the lines without stopping the other sources.

## Design details

### Package layout

Logs is its own area, next to `resources`, and depends on `resources` only for shared types
(`ObjectRef`, `ResourceType`):

```
internal/resources/
  workload/          PodMatcher: the pods a workload owns or a Service selects (Pods tab and logs)
internal/logs/
  types.go           Request, Line, Batch, Status, DownloadRequest
  interfaces.go      Opener, PodWatcher, Sink
  kube/              Opener and PodWatcher over client-go (GetLogs, pod watch)
  stream/            a stream = targets → per-container readers → merger → store + batcher
  store/             a stream's received lines on disk: append, read pages, search
  download/          writes a target's full logs to an io.Writer
```

Following the design principles of proposal 0002 (SOLID, replaceable parts), `stream` and
`download` depend only on the interfaces in `internal/logs`, and only `kube` calls client-go.

### Pods of a workload

**Rule:** a workload's Pods and Logs tabs show only the pods it **owns**. A pod must never
appear under a workload that does not own it. Label selectors alone break this rule when
selectors overlap (`app=web` also matches a `web-canary` Deployment's pods), when another
controller reuses a workload's labels (Argo Rollouts' `workloadRef`), and for hand-made or
orphaned pods with matching labels.

The API server can filter LIST and WATCH by label but not by owner. So matching is done in
two steps:

1. **Selector, on the server:** narrows the watch to the workload's `spec.selector`. A pod a
   workload owns always matches its selector (controllers adopt only matching pods and release
   pods whose labels stop matching), so this never misses an owned pod, and it keeps the watch
   small.
2. **Ownership, on the client:** of those pods, keep only the ones whose **controller**
   reference (`metav1.GetControllerOf`, the owner reference with `controller: true`) is an
   owner UID of the workload. UIDs, not names, so a workload deleted and recreated under the
   same name does not claim the old one's leftover pods until it adopts them.

| Target | Server-side selector | Owner UIDs |
|---|---|---|
| StatefulSet, DaemonSet, ReplicaSet, Job | `spec.selector` | the workload's UID |
| Deployment | `spec.selector` | the UIDs of the ReplicaSets whose controller is the Deployment |
| Service | `spec.selector` | none: selector only (below) |

- **Deployments** own pods through ReplicaSets, several at once during a rollout. The owner
  set is kept live by a ReplicaSet view in the namespace with the Deployment's selector (M2's
  table cache: rows carry `ownerReferences` in their metadata), keeping the ReplicaSets whose
  controller is the Deployment's UID. When the set changes (a rollout creates a ReplicaSet),
  pods are checked again, so a new ReplicaSet's first pods appear even if they arrive before
  the ReplicaSet does.
- **Jobs** get an auto-generated selector containing their UID, so the check almost never
  removes anything. It still runs, because `spec.manualSelector: true` allows any selector.
- **Services** own nothing. The pods of a Service are, by definition, the pods its selector
  matches, the same set its endpoints are built from. That is the only meaning a Service's Pods
  and Logs tabs can have, so they use the selector alone.
- **`workload.PodMatcher`** resolves a target into both steps:

  ```go
  // PodMatcher finds the pods of a workload or Service. It returns
  // ErrNoPods if ref's type does not manage pods or its selector is empty.
  type PodMatcher interface {
      Match(ctx context.Context, s cluster.Session, ref resources.ObjectRef) (Membership, error)
  }

  // Membership is the live set of pods that belong to one target.
  type Membership interface {
      Selector() labels.Selector     // for LIST/WATCH
      Owns(pod metav1.Object) bool   // the ownership check; always true for a Service
      Changed() <-chan struct{}      // the owner set changed (Deployments); re-check pods
      State() (synced bool, err error) // not synced yet, or why ownership cannot be checked
      Close()
  }
  ```

  The implementation GETs the object with the dynamic client and converts `spec.selector`
  (`metav1.LabelSelector`, with `matchExpressions`) using `metav1.LabelSelectorAsSelector`.
  Supported kinds are a data table: `apps/v1` Deployment, StatefulSet, DaemonSet, ReplicaSet,
  and `batch/v1` Job. A `core/v1` Service's `spec.selector` is a plain label map and is
  converted with `labels.SelectorFromSet`. An empty or missing selector returns `ErrNoPods`
  rather than matching every pod (a Service without a selector is valid: ExternalName, or
  endpoints managed by hand).
- **Pods tab:** `cache.Key` gains `LabelSelector` beside `FieldSelector`, and `table.Source`
  passes it on LIST and WATCH. `view.Request` gains an optional `Keep func(metav1.Object) bool`
  filter, set to `Membership.Owns`. The tab is an ordinary view on `pods` in the workload's
  namespace with that selector and filter, so it is live, shares the informer cache, and uses
  the same `RowGrid`. A pod whose update makes it fail the filter (released by its controller)
  leaves the view like a deleted row; on `Changed()` the view re-checks its cached rows. The
  selector string is canonical (`labels.Selector.String()` sorts terms), so one workload always
  maps to one informer.
- **Fail closed:** if ownership cannot be checked (no permission to list ReplicaSets for a
  Deployment), the tabs show the error instead of falling back to the selector alone.
- The workload is read again when its `resourceVersion` changes (at most once per 2s, like
  Describe). A changed selector reopens the view.

### Log streams

A **stream** is one open Logs tab: `(target, options)`. The target is a pod, a workload or a
Service.

- **Targets:** for a pod, one pod. For a workload, the pods it owns; for a Service, the pods
  its selector matches (see [Pods of a workload](#pods-of-a-workload)). In both cases
  `stream` asks a `PodWatcher` for the pods as **full objects**, because it needs container
  names, states and restart counts, which the M2 table rows do not carry. `kube` implements it
  with one filtered watch per stream (`metadata.name=<pod>` or the label selector, in one
  namespace), and `stream` drops pods that fail `Membership.Owns`, re-checking on
  `Changed()`. A pod that stops being owned has its sources closed. The watch is separate
  from the table cache on purpose: it stores few objects, lives exactly as long as the tab, and
  keeps `cache` free of full objects.
- **Sources:** each `(pod, container)` is a source with its own reader, opened through
  `Opener` (client-go `Pods(ns).GetLogs(name, opts).Stream(ctx)`). The request always sets
  `timestamps: true`; the backend parses and strips the timestamp, so the UI can show or hide
  it without restarting, and resume can use it. A source is opened when its container has
  started (running or terminated). Waiting containers show as "waiting: ContainerCreating" in
  the status strip.
- **No pod limit:** every matching pod is streamed (`kubectl logs -l` stops at
  `--max-log-requests`, default 5). Each source is one long-lived request, proxied by the API
  server to the pod's kubelet, so to keep a large workload from hitting the API server all at
  once, sources are **opened at most 10 at a time**; the rest queue and start as earlier ones
  connect. Long-running requests like these are not counted against the
  API server's in-flight request limits. The pod picker narrows a stream to chosen pods.
- **Merging:** lines are forwarded in arrival order. Lines from one source keep their order;
  lines from different sources are not re-sorted by timestamp (that would need a delay to wait
  for late sources). Download does sort them (see [Download](#download)).
- **Container restarts:** while following, the kubelet ends a log request when the container
  exits. When the pod watch shows that container running again with a higher
  `restartCount`, the source reopens with `sinceTime` set to its last line's timestamp and
  emits a `restarted` marker.
- **Connection drops:** every stream's context is a child of `Session.Ctx`, so a disconnect
  ends all its sources and the stream reports `stale`. The UI keeps the lines. When M1
  reconnects, the UI restarts the stream with `resume: true`; each source reopens with
  `sinceTime` = its last timestamp and skips lines it already sent (the same timestamp and
  the same count of lines at that timestamp). A `resumed` marker shows where the gap was.
- **Ending:** a stream ends when its tab closes (`Stop`), its target is deleted, or follow is
  off and every source reached EOF.

### Line handling

- Lines are split on `\n`, with `\r\n` normalized. A line longer than **16 KiB** is cut and
  ends with `… [N bytes truncated]`, so one giant line cannot blow up memory or the renderer.
- Invalid UTF-8 is replaced with U+FFFD. ANSI escape sequences are stripped, so search matches
  what is shown. Rendering colours is a possible follow-up.
- Every line gets a **sequence number** (`seq`), increasing within a stream, in merge order.
  It addresses lines in the store, in pages and in search results.
- **Batching:** like table views, each stream flushes live lines to the UI at most every
  **100ms**, with at most **5,000 lines per batch**. Every line goes to the store first. If
  more than 5,000 arrive within one window, only the newest are sent and the batch reports
  `skipped`, shown inline as `── 12,345 lines not shown live (output too fast) ──`. Nothing
  is lost: scrolling up loads them from the store.

### Line store

Received lines live in Go, on disk, not in the UI. The UI holds only a window around what is
on screen.

- **Files:** each stream writes to its own directory under the user cache dir
  (`os.UserCacheDir()/kuberoot/logs/<stream ID>/`, directory `0700`, files `0600`). Lines are
  appended as records (`seq`, source index, timestamp, text) to **8 MB segment files**.
- **Size cap:** **100 MB per stream** by default (about 500,000 lines of 200 bytes), set in
  Settings to 25, 50, 100 or 250 MB. Only one Logs tab is open at a time, so this is also the
  total. When the cap is reached the oldest segment is deleted, and the top of the view says
  "Older lines were dropped (100 MB limit). Download for the full log."
- **Index:** in memory, the file offset of every 256th line per segment, so reading any page
  is one seek and a short scan. About 1 KB of index per 100,000 lines.
- **Cleanup:** a stream's directory is deleted when the stream is stopped or restarted with
  new options, and on app exit. Directories left by a crash are removed at startup.
- **Pages:** the UI asks for lines by position: `Lines(streamID, view, fromSeq, count)`, where
  `view` is `all` or `matching`. Reads go to the segment files through the OS page cache, so
  recently written pages are served from memory.
- **Search** runs in Go, over the store, so it covers every received line, not just the ones
  on screen. Setting a query scans the store in the background, reporting progress and the
  match count, and keeps a list of matching `seq`s. New lines are matched as they are
  appended. Next/previous asks Go for the nearest match from the current position. Regex uses
  Go's `regexp` (RE2 syntax). Lines sent while a search is set carry their match ranges, so
  highlighting uses the same engine and the UI never runs its own regex.
- **Only matching** pages over the list of matching `seq`s instead of all lines.
- **Save received lines** copies from the store to the chosen file in Go (all, or matching
  only), with the prefixes and timestamps currently shown. Nothing crosses the bridge.

### Download

- `Download` opens the native save dialog (Wails `Dialog.SaveFile()`), then writes from Go
  straight to the file. Nothing passes through the UI, so size is not limited by the line store.
- It requests the full log (no tail, no since, no follow) with the current container,
  previous and timestamps options.
- For a workload or Service, each source is read into a temporary file, one after another
  so a download adds at most one request at a time. The files are then merged by timestamp
  into the target file, with a `pod/container` prefix, and deleted. Memory stays flat however
  large the logs are.
- Default file name: `<pod-or-workload>[-<container>]-<YYYYMMDD-HHMMSS>.log`.
- The UI shows progress (bytes written) and can cancel; a cancelled download deletes the
  partial file.
- **Save received lines** opens the save dialog and copies from the [line store](#line-store),
  with the same progress and cancel as a download.

### Go<->UI contract

New service `app.LogService`, a thin wrapper over `internal/logs`, and one new method on
`ResourceService`:

```go
func (s *LogService) Containers(ref resources.ObjectRef) (logs.Containers, error)
func (s *LogService) Start(req logs.Request) error // lines and status arrive as events
func (s *LogService) Stop(streamID string)
func (s *LogService) Download(req logs.DownloadRequest) (string, error) // path written, "" if cancelled
func (s *LogService) CancelDownload(downloadID string)
func (s *LogService) SaveLines(req logs.SaveRequest) (string, error) // path written, "" if cancelled
func (s *LogService) Lines(streamID string, view logs.View, fromSeq uint64, count int) (logs.Page, error) // count < 0 reads backwards
func (s *LogService) SetSearch(streamID string, q logs.Search) error // empty Text clears it
func (s *LogService) SeekMatch(streamID string, fromSeq uint64, forward bool) (uint64, bool, error)

func (s *ResourceService) OpenPods(viewID string, ref resources.ObjectRef) error
```

As with views, the UI chooses the stream ID and routes events for it before calling `Start`.
Changing options is `Stop` + `Start` with a new ID; an in-place update is not worth the code.

Types sent to the UI:

```go
type Containers struct {
    Default    string      `json:"default"`
    Containers []Container `json:"containers"`
    Pods       []string    `json:"pods,omitempty"` // workloads and Services, for the pod picker
}

type Container struct {
    Name string `json:"name"`
    Kind string `json:"kind"` // container | init | ephemeral
}

type Request struct {
    StreamID     string              `json:"streamId"`
    Target       resources.ObjectRef `json:"target"`    // a pod, workload or Service
    Container    string              `json:"container"` // "" = default, "*" = all containers
    Pods         []string            `json:"pods,omitempty"` // workloads and Services: chosen pods; empty = all
    Follow       bool                `json:"follow"`
    Previous     bool                `json:"previous"`
    TailLines    int64               `json:"tailLines"`    // per container; 0 = all
    SinceSeconds int64               `json:"sinceSeconds"` // 0 = no limit
    Resume       bool                `json:"resume"`       // continue a stale stream
}

type Line struct {
    Seq     uint64    `json:"n"`
    Source  int       `json:"s"` // index into Status.Sources
    Time    time.Time `json:"t"`
    Text    string    `json:"x"`
    Matches [][2]int  `json:"m,omitempty"` // byte ranges of search matches, when a search is set
}

type Batch struct {
    StreamID string   `json:"streamId"`
    Lines    []Line   `json:"lines"`
    Markers  []Marker `json:"markers,omitempty"` // restarted, resumed; placed by seq
    Skipped  int      `json:"skipped,omitempty"` // stored but not sent live
    First    uint64   `json:"first"`             // oldest seq still in the store
    Total    uint64   `json:"total"`             // lines received so far
}

type View string // "all" | "matching"

type Page struct {
    Lines   []Line   `json:"lines"`
    Markers []Marker `json:"markers,omitempty"`
    AtStart bool     `json:"atStart"` // no older lines in the store
    AtEnd   bool     `json:"atEnd"`   // no newer lines yet
}

type Search struct {
    Text          string `json:"text"`
    Regex         bool   `json:"regex"`
    CaseSensitive bool   `json:"caseSensitive"`
}

type SearchStatus struct {
    StreamID string  `json:"streamId"`
    Matches  int     `json:"matches"`
    Scanned  float64 `json:"scanned"` // 0..1 while the background scan runs
    Error    string  `json:"error,omitempty"` // e.g. an invalid regex
}

type Status struct {
    StreamID string         `json:"streamId"`
    Phase    string         `json:"phase"` // starting | streaming | ended | stale | error
    Sources  []SourceStatus `json:"sources"`
    Message  string         `json:"message,omitempty"`
}

type SourceStatus struct {
    Pod       string `json:"pod"`
    Container string `json:"container"`
    Phase     string `json:"phase"` // waiting | streaming | ended | forbidden | error
    Message   string `json:"message,omitempty"`
}
```

Lines refer to their source by index (short JSON keys too), so a busy workload stream does not
repeat pod and container names on every line. New sources are appended, so indexes never
change during a stream; `Status` is re-sent whenever the source list or a phase changes.

Events:

| Event | Payload | When |
|---|---|---|
| `logs:lines` | `Batch` | ≤10/s per stream |
| `logs:status` | `Status` | sources added or changed, phase changes |
| `logs:search` | `SearchStatus` | search set, scan progress (at most 4/s), match count changes |
| `logs:download` | `{downloadId, bytes, done, error}` | progress, at most 4/s |

### Frontend

Under `frontend/src/lib/logs/`:

- `LogsTab.svelte` is a detail tab (`DetailTabProps`) with the toolbar, status strip, search
  bar and the log view. `PodsTab.svelte` in `resources/detail/` wraps `RowGrid` like the
  Events tab.
- `logs.svelte.ts` holds the stream state: the **window** of loaded lines (at most **5,000**,
  a few MB), the source list, markers, the stream's `first`/`total`, and the search status.
  It holds no other lines and runs no search itself.
- **Windowed scrolling:** while following, live batches append to the window and the oldest
  lines are trimmed from its top. When the user scrolls within 1,000 lines of the window's top,
  the next 2,000 older lines are fetched with `Lines` (backwards) and prepended, keeping the
  scroll position anchored on the same line, and the same number are trimmed from the bottom.
  Scrolling down works the same way until the window reaches the live end, when following
  resumes. The scrollbar spans the window, not the whole store; the footer shows the real
  position. Jumping to a search match, to the first line, or to the latest replaces the window
  with the page around that `seq`.
- **The log view uses the existing editor module.** `lib/editor` gains `language: 'log'` and a
  small imperative API for a windowed document, so CodeMirror's virtualized rendering, line
  wrapping, selection and copy are reused, and the rest of the app still imports only
  `CodeEditor.svelte`:

  ```ts
  export interface LogViewHandle {
    append(lines: string[]): void;          // at the bottom
    prepend(lines: string[]): void;         // at the top, keeping the scroll anchor
    trim(from: 'top' | 'bottom', n: number): void;
    replace(lines: string[], anchor: number): void; // jumps
    setDecorations(d: LogDecorations): void; // source prefixes, markers, search matches
    scrollToEnd(): void;
  }
  ```

  The pod/container prefix and timestamps are decorations, not text, so toggling them does not
  rebuild the document. "Only matching" replaces the window with a page of the `matching` view.
  Selection and copy cover the loaded window; for more, Save received lines.
- Options the user changes (tail, timestamps, wrap) are remembered app-wide in settings;
  the defaults are 1,000 lines, follow on, wrap on, timestamps off. The store's size cap is a
  setting too (default 100 MB).

### Security and RBAC

- Reading logs needs `get` on `pods/log`; the Pods tab and the pod watch need `list` and
  `watch` on `pods` in the namespace, and for a Deployment also on `replicasets`. A `403` marks the affected source or tab as forbidden,
  the same way M2 handles forbidden namespaces. No access reviews are needed: logs are
  read-only, and RBAC-aware disabling of actions comes with M4.
- Log content is the user's data and is shown as is. It is not sent anywhere and not written
  to KubeRoot's own logs. Error messages pass through `internal/redact`.
- Downloads are written only to the path the user picks in the save dialog.
- The line store puts received log lines on disk, in the user cache dir, readable only by the
  user (`0700`/`0600`). They are deleted when the stream stops and on exit, and leftovers from
  a crash are deleted at startup. Logs never go anywhere else.

### Performance

- API load: one long-lived request per streamed container (HTTP/2 multiplexed on the existing
  connection) plus one filtered pod watch per open Logs tab. There is no pod limit, so a
  100-replica Deployment with a sidecar holds 200 requests open while its Logs tab is shown,
  similar to running `stern` on it. Opening at most 10 at a time spreads out the initial tails
  (100,000 lines here), and everything stops when the tab closes. Only one panel is open at a
  time.
- Ownership costs no extra requests except for Deployments: one ReplicaSet view filtered by
  the Deployment's selector, shared through the informer cache. The check itself is a lookup
  in a small UID set per pod event.
- Backend memory: the pending batch (≤5,000 lines), the store's sparse index, and the list of
  search matches (8 bytes per match) per stream. Lines themselves are on disk.
- Disk: at most the size cap (100 MB by default) for the one open stream. A source writing
  20,000 lines/s of 200 bytes is 4 MB/s, which reaches the default cap in about 25 seconds;
  older lines are then dropped from the store, but Download still fetches everything.
- UI memory: the window of at most 5,000 lines. Counting UTF-16 strings and CodeMirror's own
  structures (about 2–3× the raw text), that is a few MB, the same after a minute or a day.
- Target: a source writing 20,000 lines/s keeps the UI responsive (scroll, search, typing) on
  all three platforms, with skipped lines reported.

## Test plan

- **`workload`:** selector conversion for each kind (matchLabels, matchExpressions, a
  Service's map), empty and missing selectors, unsupported kinds. Ownership: a pod owned by
  another controller, a pod with no controller, a non-controller owner reference, a
  same-named recreated workload (different UID), a Deployment's owner set across a rollout
  (two ReplicaSets, then one), `Changed()` firing, and a `403` on ReplicaSets failing closed.
- **`table` / `cache` / `view`:** label selector on LIST/WATCH and in the informer key; the
  `Keep` filter, a row leaving the view when it stops passing, and re-checking on `Changed()`.
- **`store`:** append and read pages forwards and backwards across segment boundaries,
  the size cap deleting the oldest segment (`first` advancing, a page before it reporting
  `AtStart`), search over existing and newly appended lines, plain/regex/case, an invalid
  regex, the `matching` view, save of all and of matching lines, cleanup on close and of
  leftover directories at startup, and file permissions.
- **`stream`:** with fake `Opener` and `PodWatcher`: line splitting, long lines, invalid
  UTF-8, ANSI stripping, `seq` order, the batcher (100ms window, 5,000-line cap, `skipped`
  lines still in the store), source indexes,
  opening at most 10 sources at a time, the pod picker, restart reopen with `sinceTime`, resume de-duplication on
  equal timestamps, cancellation via `Session.Ctx`, and a `403` on one source.
- **`kube`:** an `httptest` API server serving `/log` with chunked follow output, `previous`,
  and errors (`400` container not found, `403`).
- **`download`:** full read, timestamp merge across sources through temporary files, cancel
  removes the partial and temporary files.
- **Frontend:** the window with a fake `Lines`: prepend keeps the scroll anchor, trimming
  keeps at most 5,000 lines, scrolling back down resumes following, and jumping to a match
  replaces the window.
- **`app`:** `LogService` with the injected `emit`, as for the other services.
- **Integration (kind, CI):** a pod printing a counter; follow, restart it (kill the
  process), check no line is lost or repeated; a 3-replica Deployment scaled to 5 and back to
  1, checking sources come and go; a Service over that Deployment and one without a
  selector; a ServiceAccount without `pods/log`. Ownership: Deployments `web` (`app=web`)
  and `web-canary` (`app=web,track=canary`) plus a bare pod labelled `app=web`, checking that
  `web` shows only its own pods while a Service on `app=web` shows all of them, and a rollout
  of `web` keeping its pods throughout.
- **Manual:** kind, EKS and GKE (M1 follow-up 1), on macOS, Windows and Linux: a noisy pod
  (20k lines/s), long lines, Wi-Fi off and on while following, download of a large log, and a
  100-replica Deployment on kind for the many-sources case. Scroll from the latest line back
  to the first of a full 100 MB store, and search it, checking UI memory stays flat.

## Alternatives

- **An in-house virtualized log list** (like `RowGrid`): smaller, but fixed row heights make
  line wrap hard, and we would rebuild selection, copy and find. CodeMirror is already in the
  app behind `lib/editor`.
- **Sorting merged workload lines by timestamp while streaming:** needs a reorder delay and
  still fails for late sources. Arrival order is what `stern` and `kubectl logs -l` show.
- **A pod limit per stream** (kubectl's `--max-log-requests`, default 5): bounds API
  requests, but hides pods silently and makes the user pick. Rejected in favour of opening
  sources gradually and scaling the buffer; the pod picker narrows a stream when wanted.
- **Lines in a UI buffer** (keep the newest 10,000–250,000 lines in the page, drop older
  ones): much less code, with search in the UI. But memory grows with the buffer setting
  (10–50 MB at the larger sizes), scrolling back stops at the buffer, and search sees only
  what is loaded. Rejected for the disk-backed store with a window.
- **Only one way to save:** "Save received lines" alone stops at the store's cap; full
  download alone cannot save a filtered view. Both are offered.
- **Selector only** (what `kubectl describe` and `kubectl logs -l` do): simplest, but shows
  other workloads' pods when selectors overlap. Rejected: a workload must show only its own
  pods.
- **Ownership only:** the API server cannot filter by owner, so it means watching every pod
  in the namespace and filtering in the client. Rejected for cost; the selector narrows the
  watch first and never misses an owned pod.
- **Pod lists from the table cache instead of a separate watch:** table rows carry only cells
  and metadata, not container statuses. Storing full pods in `cache` would cost memory for
  every pod table.

## Resolved questions

1. **Pod limit:** none. Every matching pod is streamed, and sources open at most 10 at a time
   (see [Log streams](#log-streams)).
2. **Defaults:** 1,000 tail lines per container, follow on, wrap on. Timestamps are a toggle,
   off by default.
3. **Services:** included. Services get the Pods and Logs tabs, using their `spec.selector`.
4. **Save received lines:** included, next to the full download, respecting "Only matching".
5. **Which pods belong to a workload:** the pods it owns. The selector narrows the watch on
   the server and the controller reference decides, so a pod never shows under a workload
   that does not own it. Services, which own nothing, use their selector (see
   [Pods of a workload](#pods-of-a-workload)).
6. **UI memory:** lines are kept on disk in Go, capped at 100 MB per stream by default
   (25–250 MB in Settings), and the UI loads a window of at most 5,000 lines as the user
   scrolls (see [Line store](#line-store)).
